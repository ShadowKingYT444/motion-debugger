## Decision

Keep the temporal recorder. Do not add another generic taste prompt or treat lower displacement as the product objective. First require proof that the user's task works, then review composition, then spend the remaining budget on specific temporal defects. This PR tightens the existing skill accordingly and supplies a native-browser diagnostic plus a patch for the recovered Ants artifact. It does **not** claim to implement the proposed core/tool changes below or to prove an agent-quality improvement.

## 1. Proven application bug: browser timers have the wrong receiver

In Motion HTML line 156, `Workflow` defaults to native `setTimeout` / `clearTimeout`, stores them on the instance, then invokes them as instance methods:

```js
constructor({ setTimer = setTimeout, clearTimer = clearTimeout, /* ... */ } = {}) {
  this.setTimer = setTimer;
  this.clearTimer = clearTimer;
}
// line 173, abbreviated
this.timer = this.setTimer(callback, 80);
```

The native timer is called with the `Workflow` instance as its receiver. In the tested Chromium this throws `Illegal invocation`. `start()` has already emitted `status: running` and stage zero; its first tick is never scheduled. The submit listener catches the exception at line 288 and puts it in `#task-error`. Therefore `pageerror` stays empty while the product is visibly broken. This is not a GPU, easing, smoothness, or model-size problem.

A one-site change, with **no CSS, layout, animation, scenario, or workflow-duration edits**, fixes the tested timer failure:

```js
setTimer = (callback, delay) => window.setTimeout(callback, delay),
clearTimer = timer => window.clearTimeout(timer)
```

Wrap both functions: fixing only scheduling leaves clearing/pause/cancel vulnerable. The ordinary HTML already schedules through `window.setTimeout`. The [artifact patch](ants-20261003/timer-defaults.patch) preserves the original bytes apart from this replacement; its patched SHA-256 is `1e82df862360ffbcc155852b02927629b4c0483bd545cd8829ddfca30fd066f3`.

## 2. Why the current plugin can fail to catch this

These are source-grounded limitations and workflow failures, not a claim that the unseen Ants agent executed a particular recipe.

### Functional success is optional, while motion measurements are prominent

In current [`capture.ts`](../../packages/core/capture.ts), `browser-errors` means **no uncaught page errors**. In [`analysis.ts`](../../packages/core/analysis.ts), success assertions about final text, visibility or attributes are emitted only when the caller supplies `contract.final`. The timer bug is caught by the app. A stationary target with adequate sampling can satisfy position/height upper bounds without completing a task. Even equal final states can mean equally stuck pages.

The existing [workflow skill](../../plugin/motion-debugger/skills/motion-build-inspect-repair/SKILL.md) already says to preserve final state and test controls. The gap is not the absence of those sentences: the delivery process still needs an explicit positive task result, a meaningful deadline, and a visible-error check. Browser API compatibility must be tested with native browser APIs, not exclusively mocks or a Node timer implementation.

**Change:** Keep free-form capture useful for investigation, but distinguish `capture completed` from `user journey passed`. A build-delivery gate must refuse a success label without positive completion evidence. For this artifact: submit -> `#workflow[data-status="complete"]`, progress 100, useful result shown, `#task-error` hidden; then verify replay and interruption. Merely matching `visible: true` on the workflow container is insufficient.

### Observation is still much narrower than a visitor's experience

Current [`frames.ts`](../../packages/core/frames.ts) returns a maximum of six images; its default is only three frames around the first finding at `t-100`, `t`, `t+100` ms. Without a finding it uses the capture midpoint. It downscales frames to fit 720 x 540. These are real image responses, but three stills over 200 ms are not a six-second task, an entrance sequence, or a full-resolution typography review. A caught functional error need not create a motion finding, so automatically selected frames need not cover the important state.

Current capture defaults to 2,400 ms; Ants Motion's stages total 6,000 ms. The probe starts after navigation with `networkidle`, diagnostics and the poster screenshot. Thus initial entrance geometry is outside the measured probe window, although pre-roll pixels may remain in the recording. This is a coverage gap, not proof that the video lacks every initial frame. Playwright itself [discourages using networkidle as a test-readiness criterion](https://playwright.dev/docs/api/class-page#page-goto-option-wait-until).

**Change:** Select times from the user journey, not only detector findings: onset, handoff, interruption, result/error. Include a full-page composition review and native-resolution target crop alongside the low-resolution overview. Make an explicit load/entrance capture mode with a defined time origin, and bounded readiness/outcome conditions instead of equating an elapsed wait with success. Keep recordings and numerical traces distinct; approximate video alignment must remain labeled. Do not relax the cadence gate to manufacture a smoothness pass.

### A motion bug detector is not a frontend art director

The preview's [`motion-design`](../../plugin/motion-debugger/skills/motion-design/SKILL.md) skill already discusses hierarchy, typography, restrained decoration, responsive composition and real controls. Adding another version of that generic advice is unlikely to resolve an acceptance failure by itself.

In the rendered Ants hero screenshots, the ordinary page uses a larger, more concentrated headline and an orbit of small agent/task illustrations. The Motion page introduces a large outlined ant holding a card, a longer headline, and additional narrative elements. My visual reading is that the ordinary version has a clearer initial copy/action/illustration relationship; this is a design judgment, not an objective score. The two outputs also change scenarios and interaction structure. The timer-only patch preserves the Motion composition, so fixing the crash does **not** establish that it now looks better.

**Change:** Separate creation from debugging. During repair, freeze the approved layout, copy, assets, feature set and motion intent unless a change is necessary to fix the defect. Before accepting any candidate, compare the actual before/after desktop and narrow frames for hierarchy, readability, composition and task clarity. On taste alone, accept a tie/no-op over a speculative rewrite. For from-scratch design, establish a concrete reference direction and judged examples; do not make a detector's numerical score a proxy for taste.

## 3. The repository's own trial exposes the workflow cost

The [MONO study](../../studies/workflow-mono-20261003/README.md) is unusually useful because it preserves failures. Both arms had the same brief and twenty-minute wall budget. The ordinary agent completed early. Motion hit its hard stop after one evidence-led repair; its comparison and final report were unfinished. It had reduced a drawer displacement but left Undo unclickable. The normalized contract still failed. The agent's headed frames were cropped, while all six final desktop recordings failed the 80 ms sampling gate. This does not establish that the app itself stutters as recorded: runner/rendering cost is a confound.

This supports a concrete **budget-allocation and observation-fidelity failure in that trial**. It does not prove every extra tool call is harmful or identify the cause of Ants' aesthetic differences. More mandatory capture calls can leave less time to finish the product. A successful tiny doctor recording also does not guarantee that a heavy 3D page yields usable pixels or cadence.

**Change:** Run a cheap native-browser functional smoke test before a multi-call temporal investigation. Calibrate representative-page recording once, cache that result for the runtime, and stop making temporal claims when it fails. Reserve verification time inside the total budget, so an unfinished candidate cannot displace the last working version. Keep the two-attempt temporal-repair bound, but do not require fixing a lower-priority easing issue before an identified broken primary control. Consider one combined review call with requested journey frames plus compact findings to reduce orchestration overhead; avoid forcing every call on a page with no observed temporal defect.

## 4. Prioritized implementation contract

| Priority | Change | Acceptance test |
| --- | --- | --- |
| P0 | Fix the generated Ants timer defaults | Native browser completion and pause/resume/cancel/replay pass; preserve original artifact and patch hash |
| P0 | Functional-first delivery gate | A caught exception + stable DOM + no pageerror cannot be labeled a successful product; missing outcome evidence is `unverified`, not `passed` |
| P1 | Outcome/absence conditions in recipes or host acceptance tests | Bounded success selector/text/attribute checks and forbidden error-state checks; no arbitrary JS required; exploration can still omit them |
| P1 | Journey-aware visual evidence | Delayed six-second completion, initial entrance and interrupted transitions are covered; frames identify requested time, actual seek and viewport/crop |
| P1 | Page-level and target-level visual regression review | Preserve approved composition during a narrow fix; judge actual pixels, not CSS adjectives or lower displacement |
| P1 | Representative recording health + explicit time budget | Cropped/oversparse evidence is inconclusive; last verified working build survives budget expiry |
| P2 | Attribute real agent improvement | Separate skill-only, tools-only, combined and ordinary workflows under matched budgets; retain every attempt |

This PR implements only the **host-skill clarification, artifact patch and diagnostic**. The core remains unchanged: no renamed success field, mandatory final schema, new outcome selector, live stream, extra frame resolution, or automated acceptance engine is implied. This avoids introducing an untested schema/runtime change into the existing stacked preview fixes.

## 5. The next experiment should test the actual promise

Run two distinct evaluations rather than calling independent pages “before and after.” For debugging, start agents from identical broken source with held-out native-browser journeys. For design, use the same brief/assets/constraints and blind human preference judgments on complete outputs. Keep ordinary agents' normal browser and screenshot tools available.

Use four arms—ordinary, skills only, temporal tools only, both—to separate design guidance from observation cost. Freeze model/build, budgets and tasks before running; log installed plugin hash, wall/tool time, whether returned images were actually inspected, final artifact hash, and all failures. Use repeated tasks/runs and report uncertainty rather than generalizing one pair.

Primary outcomes: task completion without regression, then blinded visual/motion preference among functional outputs. Report motion-contract pass rate and debugging time separately. Do not erase a failed journey because a later video avoided that control. A timer-wrapper fix proves a local code cause; a lower displacement proves a measured contract change; neither alone proves the plugin makes agents better designers.
