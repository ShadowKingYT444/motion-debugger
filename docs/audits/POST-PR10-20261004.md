# Post-PR #10 audit: remaining contract bugs

Audited source: [`fde065cdea0aecb4631e9106b48e0b53e327a8df`](https://github.com/ShadowKingYT444/motion-debugger/commit/fde065cdea0aecb4631e9106b48e0b53e327a8df), inspected 4 October 2026. This is a focused review, not a certificate that the repository has no other bugs. PR #10 is closed, not recorded as merged; this audit concerns the implementation now on `main`.

## Decision

Fix the four issues below before using `motion_review` or `motion_probe` results to choose a launch-demo winner. The upgrade is real: actor observations, transition-plan validation, event-centered review, interruption probes, and authoring helpers exist. This report does not propose adding those features again.

This PR changes documentation and opt-in diagnostic files only. It does not fix the runtime, change thresholds, merge anything, or alter frozen studies. Its regression specifications intentionally fail on the audited source. The more ambitious from-scratch demo is specified in [FIELD](../FIELD-SCROLL-DEMO.md).

## Executed checks and limits

Seven deterministic unit cases were executed against hash-verified source functions: two controls passed and five regression assertions failed. They cover four defects; R1 has both complete-omission and partial-omission cases. The fixtures are synthetic, not recorded browser evidence.

Two additional native Chromium fixtures reproduced R2 and R3 using unforced clicks, actual Web Animations, and rAF-observed geometry. The collector is independent of the shipped browser probe. Its samples were processed by the shipped actor-analysis and review functions. Both traces met the actor analyzer's existing coverage requirements. These runs did not exercise the complete capture/MCP transport or record video. Geometry response is not pixel-presentation latency.

The execution environment had Node 22.16.0, system Chromium 144.0.7559.96, and a preinstalled Playwright driver 1.57.0-beta-1764944708000. Network/DNS prevented cloning and installing the repository's locked dependencies. Exact source files were checked against their Git blob hashes. TypeScript transpilation preserved the tested function bodies; the local adapter selected those functions and substituted module loading only. Plan validation used the preinstalled driver's bundled Zod, not the repository's locked Zod. This is **not** a clean-checkout, locked-dependency, full-browser-suite, or native-agent-host pass.

## R1 — P1: a review accepts removal of required error checks

**Code:** [`reviewRecipe`, review.ts:25–44](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/packages/core/review.ts#L25-L44); [the plan's required error exclusions](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/packages/core/transitions.ts#L25-L27).

The plan declares `acceptance.forbiddenVisible`, but `reviewRecipe` only binds actor measurements and identities. A recipe with an empty error-selector list passes validation against a plan requiring `#error`. A recipe that keeps `#error` but omits a second required selector, `#fatal`, also passes. Neither case needs malformed inputs.

This is not the old claim that outcomes do not exist. They do. The bug is that the execution recipe can weaken this part of its declared plan without rejection. A positive completion marker can coexist with a visible error that the effective recipe no longer checks.

**Repair contract:** require the recipe to contain every plan-required forbidden selector, or derive an effective union before capture and persist that exact effective recipe. Extra recipe checks are allowed. Reject unsupported total sizes; do not truncate silently. Missing `contract.outcomes` must not bypass a nonempty required exclusion list. Do not pretend the free-text `usefulCompletion` sentence can automatically become an executable predicate; bind useful outcomes explicitly in a versioned schema.

**Regression cases:** complete omission, partial omission, a valid superset, missing outcomes, and capture reuse with the effective recipe. Reproduce a visible excluded error alongside a positive result in the full native suite.

## R2 — P1: all actors are timed from the first input on the page

**Code:** [`reviewSummary`, review.ts:72–86](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/packages/core/review.ts#L72-L86).

For each actor, the summary finds the first trusted input anywhere in the capture. It does not resolve that actor's beat trigger or the latest relevant input. An earlier click on an unrelated control therefore becomes the start of a later actor's response clock.

The deterministic case changes an unrelated control at 100ms, triggers the actor at 600ms, and observes its first movement at 620ms. Actual response from the relevant input is 20ms; the review reports 520ms and fails an 80ms bound. In the native fixture, the same error produced **28.5ms versus 493.5ms**, again with adequate actor coverage.

This becomes especially harmful on a long scroll page. An early hero interaction must not time the later gallery, product inspection, and waveform editor. It can push the agent to shorten correct transitions to compensate for an incorrect clock.

**Repair contract:** bind each acceptance window to a concrete beat and relevant input/action identity. Keep each retarget as a new input epoch; honor `winner: latest-input`. Group pointer-down/up/click as appropriate for the declared trigger rather than counting them as unrelated user decisions. Evaluate response and velocity around that epoch. If attribution is unavailable, return `unverified`, not a confident response failure or pass. Preserve existing plans through an explicit compatibility path rather than guessing triggers from prose.

**Regression cases:** unrelated earlier controls, two actors with different triggers, repeated retargets, multiple pointer events for one activation, reverse scroll, and no attributable input. Check the whole input sequence, not just the first movement.

## R3 — P1 for terminal acceptance: an old arrival can survive a wrong final pose

**Code:** [actor-analysis.ts:40–50 and 72](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/packages/core/actor-analysis.ts#L40-L50).

The arrival loop stops permanently after its first qualifying destination dwell. It never examines later samples for departure. In the fixture, the actor reaches x=100, holds long enough, then moves to x=300 without another input. Its required terminal destination is still x=100. The actor arrival assertion and review's settling status remain `passed`. Native Chromium reproduced the 200-CSS-pixel endpoint error while the arrival assertion stayed passed.

A historical waypoint may legitimately pass after departure. A terminal destination that must remain until another input must not. The current plan/recipe binding does not make that distinction executable. The reproduction's plan explicitly requires the selected part to remain at its destination; its generic completion marker cannot rescue the missing endpoint check.

**Repair contract:** distinguish waypoint acceptance from terminal acceptance. Associate each destination with an input epoch and required hold interval. For terminal acceptance, require the actor to remain within tolerance through the declared end or next relevant input. Departure must invalidate the previous terminal result. Keep entry time and confirmation time separate and define which clock the limit uses. Do not call an intentional new transition a failure merely because it leaves an old waypoint.

An explored hypothesis was **not** counted as a separate bug: reporting the start of a verified stable interval as settling time can be valid. A dwell used to confirm stability need not automatically be added to that settling-time definition. The confirmed problem is accepting an obsolete arrival despite a wrong terminal pose.

**Regression cases:** reaches/holds/leaves with no new input; arrives then receives a legitimate new target; interrupted dwell; terminal versus waypoint intent; and sparse coverage that must remain unverified. Add a native final-pose check independent of the application's own `done` label.

## R4 — P2: incomplete capture takes priority over an already observed product error

**Code:** [replay.ts:18–23](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/packages/core/replay.ts#L18-L23), [retained capture failure path](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/packages/core/capture.ts#L240-L264).

`probeClassification` returns `infrastructure-failure` immediately for every incomplete report. The unit case includes an already observed visible `#error` and failed functional delivery, followed by a later incomplete action. The top-level classification still becomes infrastructure failure. The raw evidence is not deleted, but the product failure is hidden by the classification used to select failure cases for minimization.

A timeout alone does not prove a product defect. The control with an incomplete capture and no established defect correctly remains an infrastructure failure. Preserve that distinction.

**Repair contract:** report capture health and established product assertions separately. A known visible forbidden state must survive a later recording/action failure. Do not treat missing observations or a timeout alone as proof that an app is broken. Only minimize a case against the same specific product-failure signature; do not minimize away the action that exposed it.

## What is not being reported as a new defect

Scene poses are explicitly app-reported, and the implementation does not grant them an independent pixel pass. Orientation and some projection checks remain explicitly unverified. Those are capability limits, not concealed successes. The bounded color-mask helper is a diagnostic fixture tool, not a general WebGL object tracker. The 80ms evidence gate remains unchanged and is not a display-FPS certificate. No conclusion here reopens the completed Ants timer investigation.

## Why the current launch demo still misses the target

The [SIGNAL study record](https://github.com/ShadowKingYT444/motion-debugger/blob/fde065cdea0aecb4631e9106b48e0b53e327a8df/studies/rail-dispatch/README.md) describes an eight-minute, from-scratch console build per arm. It reports one recipe call, three captures, and three frame calls in the assisted arm; its retained inventory does not demonstrate the new review/probe path. Individual actor response/velocity contracts and general superiority remain unverified. Both apps pass the named functional journeys.

The problem is not that trains have no meaningful motion. It is that this bounded console is a weak demonstration of a sustained scroll narrative, cross-section identity, and competing user inputs. A larger finished site plus a real, source-bound before/after refinement inside that build would make the added workflow easier to judge. [FIELD](../FIELD-SCROLL-DEMO.md) specifies that next experiment without claiming its outcome in advance.
