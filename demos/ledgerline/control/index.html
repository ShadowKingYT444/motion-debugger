Payments are easy to start and brutal to get right. Ledgerline makes every movement of money atomic, auditable and instant, so your team ships product instead of reconciliation scripts.

Anatomy of a payment

Follow one payment, from request to reconciled.

  1. 01

    Request

    Your app calls POST /v1/transfers with an idempotency key. We authenticate, validate and dedupe before anything moves.

  2. 02

    Post and hold

    Balanced entries commit atomically across regions, moving funds from available to pending. Balance checks happen in the same write.

  3. 03

    Settle

    Smart routing picks the fastest rail the beneficiary supports and falls back automatically if that rail degrades.

  4. 04

    Reconcile

    The rail confirmation is matched to the ledger entry, the books close for that payment, and your webhook fires.

Developers

An API you can read in one sitting.

Fourteen endpoints, one object model, and the same behavior in sandbox and production. If you can read the request, you can predict the ledger.

  • Idempotent by design

    Every write takes an idempotency key. Retry freely: you get the original result, never a duplicate payment.

  • Typed SDKs in six languages

    Generated from the same spec as the API, so types, errors and pagination match what the server does.

  • Webhooks that replay

    Signed events with at-least-once delivery, an ordered stream per account, and one-click replay from the dashboard.

  • Sandbox with time travel

    Fast-forward settlement, fail a rail on demand, and rewind the ledger to test the awkward paths before production does.

Questions

The details engineers ask first.

How does the ledger guarantee that it always balances?

Every transaction is a set of entries whose debits equal its credits. The write is rejected unless that holds, and it commits atomically on a cross-region quorum. Entries are append-only and hash-chained, so corrections are new entries, never edits.

Which rails and currencies are supported?

RTP, FedNow, ACH, wires, SEPA (credit transfer and Instant), Faster Payments and card settlement across 38 currencies. Routing is automatic by default, and you can pin a rail or set a fallback order per transfer.

Can we migrate an existing ledger without downtime?

Yes. Import historical entries in bulk with their original timestamps, run both systems in shadow mode, and compare balances continuously before you cut over. Most teams migrate one product line at a time.

What happens to in-flight payments during a regional outage?

Writes keep committing on the remaining two regions. In-flight transfers resume from the last committed state, and idempotency keys ensure that client retries return the original result rather than creating a second payment.

Is there a sandbox, and does it behave like production?

The sandbox runs the same code path as production with simulated rails. You can fast-forward settlement, inject rail failures, and rewind the ledger to a prior point to test edge cases deterministically.
