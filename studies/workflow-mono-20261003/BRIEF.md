# MONO: an interactive audio product launch

Build an aesthetically impressive, responsive product site for MONO, a fictional high-end over-ear headphone. This is an original agent-generated app, not a defect fixture. The visitor explores the product, chooses a material, sees the chosen product and price in a cart, and can revise that choice without losing context. Make every exposed control useful. No external APIs, stock product images or credentials.

Create a coherent editorial visual system: warm near-white, graphite type, one restrained vermilion accent, crisp geometry, expressive but readable typography, considered spacing and confident hierarchy. Use a real procedural Three.js headphone hero with believable ear cups, headband, materials and lighting. The hero should feel like a product photograph that can be explored, not a spinning toy. Keep geometry/draw calls modest; use a simple staged shadow, not expensive dynamic shadow maps.

Make this a real motion-rich experience: a scroll-linked product presentation, coordinated section/text reveals, material changes reflected in both the 3D object and product details, purposeful hover/focus/press states, a responsive specification/acoustic section, an animated sticky purchase control, a cart drawer with quantity/remove/undo or other meaningful reversible actions, and a small loading state. Use interaction-driven motion to preserve context. Avoid decorative particle clouds, arbitrary floating cards and gratuitous effects. Do not add fake bugs to create a repair opportunity.

Support rapid material changes, orbit/reset, drawer interruption/reversal, scroll interruption, retained selections, keyboard use, mobile at 360px and reduced motion. The cart can be a local demonstration, but its quantities, selections and total must work. Label the concept and local checkout scope plainly. Do not pretend a real payment or remote service exists.

Use vanilla TypeScript or JavaScript, CSS, Vite and Three.js. Prefer the existing locked local versions (three 0.180.0, vite 7.3.6). No additional UI framework. Use system/local fonts. Build and inspect the result in the connected user's Chrome using supported CUA tools. Keep it bounded and never touch unrelated browser tabs or processes. Deliver a usable first version, real source and a concise execution record. The coordinator will freeze this exact output before either repair arm starts.
