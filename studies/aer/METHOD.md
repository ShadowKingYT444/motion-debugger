# AER paired agent case study

This is one paired demonstration, not a general benchmark or causal estimate.

- Same product brief in PROMPT.md
- Same requested model: gpt-6.1-sol; reasoning effort: high
- Separate agents and source directories; each agent was instructed not to inspect the other arm (not an operating-system access sandbox)
- Initial-build allowance:25minutes each; evidence-led repair allowance:20minutes each, excluding mechanical browser-run waiting
- Baseline: ordinary coding/browser evidence, without this project's plugin or new skills
- Treatment: this project's frozen design/3D/workflow skills plus actual Motion Debugger captures and recorded-frame tool responses
- No supplied repair implementation or authored before/fixed switch in either application
- Shared functional/viewport checks and honest reporting of failures

The agents run in a restricted cloud workspace. A coordinator mechanically copies frozen source to a GitHub Actions browser runner and returns requested raw evidence. The coordinator does not supply diagnoses or source fixes to the builder agents. This bridge is an environment accommodation, not a claim that a local plugin was installed in every interactive host.

Model execution is not seeded or token-budget identical. Timing, iteration count, requested evidence and tool availability are recorded. Differences cannot be attributed solely to the skills from one pair. A good baseline must not be intentionally degraded.

Public execution records include prompts, source snapshots/diffs, requested checks, tool outputs, recordings and the agents' concise diagnoses/fixes. They do not contain private chain-of-thought.

AER is a fictional demonstration concept. No external customer system is modified. Repository/public registry publication remains deferred.

## Recorded execution conditions

Both builders requested gpt-6.1-sol at high reasoning effort. Actual elapsed implementation time differed; there was no token- or randomness-matched execution. Each selected its own pinned dependencies. Native skills were provided as the same files shipped in the plugin, and requested MCP calls were executed by the mechanical CI bridge. This does not establish automatic discovery inside every supported editor.

The first treatment request exceeded the existing 16-action schema and was rejected. Its original request and error remain evidence; a corrected supplemental recipe is labelled separately and must run against both initial and repaired source. Initial evidence also exposed a tool-side omission of accessibility/boolean final attributes; the corrected observer is used for both sides of the final temporal comparison.

The reusable fixture regression suite permits at most three attempts only when the unchanged sampling-integrity gate fails. It preserves every capture and never retries a valid capture merely because a motion assertion failed. A weak recording remains inconclusive, not a pass.

The exact four experimental skill folders are preserved under inputs/skills with SHA256 hashes. The release workflow skill received explicit bounded-DAG routing after those inputs were frozen, following the user’s later request. That instruction update is not retroactively attributed to the study.

After the first treatment repair, the original builder session could not be resumed because of the agent-thread limit. A separate Motion QA worker, instructed not to inspect the baseline, continued the second bounded repair with the remaining time allowance. The original same-model pair and first-repair evidence remain separately identifiable; this continuation is not presented as a fully controlled same-session A/B result.
