The product

One payment, four moves.

  1. 01

    One call, one idempotency key

    Your service posts a transfer. Retry it a hundred times and Ledgerline records it once.

  2. 02

    Entries land in pairs

    A debit and its credits commit atomically, so the books can never be half updated.

  3. 03

    Proof, not reconciliation

    Every commit asserts debits equal credits before it is visible. If it cannot balance, it never exists.

  4. 04

    Events with receipts

    Signed, ordered webhooks go out carrying the ledger version they describe.

The API

An API that reads like the accounting it replaces.

Resources are accounts, transfers and entries. There is no state to guess at: every call is idempotent, every response carries the ledger version, and the sandbox behaves exactly like production.

  • Idempotent by default. Safe retries across every endpoint.
  • Double entry, enforced. Unbalanced writes are rejected at commit.
  • Signed, ordered webhooks. Replay any event from any ledger version.
  • Typed SDKs. Node, Python, Go and Java, generated from one schema.
curl -X POST https://api.ledgerline.dev/v1/transfers \
  -H "Authorization: Bearer $LEDGERLINE_KEY" \
  -H "Idempotency-Key: ord_8f21c" \
  -d '{
    "source": "acct_payer",
    "destination": "acct_merchant",
    "amount": 10000,
    "currency": "usd",
    "fee_bps": 290
  }'
import { Ledgerline } from "@ledgerline/node";

const ll = new Ledgerline(process.env.LEDGERLINE_KEY);

const txn = await ll.transfers.create({
  source: "acct_payer",
  destination: "acct_merchant",
  amount: 10000,
  currency: "usd",
  feeBps: 290,
}, { idempotencyKey: "ord_8f21c" });
