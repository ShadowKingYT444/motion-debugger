    Why a ledger, not a payments wrapper

    Most teams start by storing balances in a column. Then comes the refund, the retry, the chargeback and the audit. We believe money software should be a journal first: every movement recorded twice, never edited, always explainable. Ledgerline is that journal, with the payment rails attached.

    One request, four states

    Follow a single transfer
    down the line.

    01

    Request

    Your service posts a transfer with an idempotency key. Retry it ten times and it lands once.

    02

    Authorize

    Balance holds, velocity limits and your own risk rules run in-line, before a cent moves.

    03

    Journal

    A debit and a credit are written atomically. Immutable, hash-chained, and always summing to zero.

    04

    Settle

    The rails confirm, webhooks fire, balances update. Reconciliation is already done.

    The API

    Boring where it matters. Sharp where it counts.

    REST, JSON and typed SDKs. Every write is idempotent, every object is versioned, every event is signed. Send a request and watch the entire movement come back in a single response.

    • Idempotent by design, with 24h key replay
    • Signed webhooks with ordered delivery
    • Sandbox that mirrors production, byte for byte
    • SDKs for Node, Python, Go, Java and Ruby

    Reliability & security

    Built so the pager stays quiet.

    Money infrastructure earns trust slowly and loses it in a minute. Ledgerline is designed around the failure modes, not the happy path.

    99.998% uptime

    Trailing 90 days of write availability. One brief degradation, zero data loss.

    90 days agotoday

    Active-active regions

    Writes are quorum-replicated across three regions. Take one away and traffic reroutes.

    All regions healthy

    Immutable, hash-chained journal

    Entries are append-only. Each one commits to the one before it, so history cannot quietly change.
